# `DllUSGymFighting` complete clean-room analysis

## Provenance and scope

- Contribution role: analysis/specification only. No implementation source was
  written or consulted while preparing this document.
- Target: Pokemon Alpha Sapphire, `AS_EUR_REV2` (European revision 2), module
  `DllUSGymFighting`.
- Observation date: 2026-10-17.
- Evidence: the externally supplied target CRO and a relocation-preserving ELF
  view generated by the repository's `generate-cro-target-object.mjs` parser.
- Tools: repository CRO parser; GNU binutils 2.44 (`readelf`, `objdump`, and
  `objcopy`); Ghidra 11.3.2 ARMv6 analysis/decompiler; SHA-256.
- Public platform fact used: the module is ARM EABI5, little-endian, ARMv6K,
  with VFP instructions. Every callable boundary below is ARM state and
  four-byte aligned.

The target CRO is 12,288 bytes. Its SHA-256 identity is
`eeb1f1f36caea3a79aa0fd458aae4360a08ca46c34fe099e8210a781706bae3a`.
This digest identifies the observation without reproducing the CRO. The module
has no indexed exports or imports and no named imports. It has one named export,
31 anonymous import identities, 33 import patch records, and 44 internal
relocation records. All 77 records are `R_ARM_ABS32`.

The former public conservative inventory accepted only `func_000006FC`; Ghidra
reported 31 other ambiguous bodies. That was a publication threshold, not
evidence that the remaining bytes were data. The direct-call graph, relocated
vtable entries, ordinary returns, and literal references give the complete
partition below. Boundaries other than `func_000006FC` and the CRO export should
remain analysis names until independently reviewed.

## Function contracts and control flow

Names in this section are neutral address names. Indirect calls are described
as `object.vtable[offset]`; no class or SDK identity is asserted.

### Small entries

- `func_000000D0(r0,r1,r2)`: save `*(r1+0x1A0)` at `r0+0x18`, call
  `func_000006FC(r0,r2)`, save the low byte of `r2` at `r0+0x1C`, then tail-call
  veneer `0x000` with `(pool_108,0,-1)`.
- `func_0000010C`: return 1.
- `func_00000114`: return without changing observable state.
- `func_00000118`: clear the word at object offset `0x20`.
- `func_0000025C`: call veneer `0x010`, then tail-call veneer `0x018`.
- `func_0000026C`: tail-call veneer `0x010`.
- `func_00000270`, `func_00000274`, `func_00000290`, and
  `func_0000029C`: return without changing observable state.
- `func_00000278`, `func_00000280`, `func_00000288`, and
  `func_00000294`: return 0.

### `func_00000124` — event poll/update

Return defaults to zero. Dispatch on `*(self+0x20)`:

- State 0: call veneer `0x008` with `(pool_24C,-1)`. On zero result, call
  veneer `0x000` with `(pool_248,0,-1)`. Load the 12-byte record at
  `*(self+0x18)+0x10`; select `*(base+0x114+4*byte[self+0x1C])`; invoke
  vtable `0xCC` with scalar `0.0f`, then vtable `0xD4` with scalar `1.0f`.
  Preserve the upper 24 bits of record word 0 and replace its low byte by 2;
  preserve the other two words. Increment `self+0x20`.
- State 1: call veneer `0x008` with `(pool_248,-1)`. On zero result, derive
  an index from bits 8..15 of record word 0, select `base+0x114+4*index`, and
  call vtable `0xD0`. Return 1 iff the returned `s0` bit pattern is at least
  the literal representation of `5.0f` under the target's signed comparison;
  otherwise return 0.
- Other states return 0.

### `func_000002A0` — record-state transition

Read the 12-byte record at `self+0x10`; the low byte of word 0 is the state.

- State 0: if byte `self+0x134` is 4, replace record state by 1 and preserve
  both coordinate words.
- State 1: read a halfword selected through the owner chain at `self+8`, using
  the caller token in pool `0x3A4`. If nonzero, for indices 0..3 call vtable
  `0xCC` on both pointer arrays at `self+0x124+4*i` and `self+0x114+4*i`, with
  `s0=1.0f` for the first array and `s0=5.0f` for the second. Replace record
  state by 3.
- State 2: tail-call `func_00000798(self)`.
- Other states return unchanged.

### `func_000003B0` — teardown

Resolve an owner object via veneer `0x028` and take its field at `+0x34`.
For `i=0..8`, call veneer `0x030(owner,*(self+0x110+4*i))`, then if that
pointer is non-null call its vtable slot `+4`. For `i=0..8`, call veneer
`0x038(self+0x14+0x1C*i)`. If `*(self+0x0C)` is nonzero, call veneer `0x040`,
then call veneer `0x018`. Finally clear `self+0x0C` and return.

### `func_00000444` — setup

Resolve the owner through veneer `0x028`, retain field `+0x34`, and initialize
the handle at `self+0x0C` through veneer `0x048` with owner fields `+0x24` and
`+0x2C`.

1. For `i=0..8`, use the nine-word descriptor vector at `.rodata+0xA4` and
   call veneer `0x050` to initialize the 28-byte inline record
   `self+0x14+0x1C*i`.
2. For `i=0..8`, use one 12-byte descriptor at `.rodata+0`. Call veneer
   `0x058` to populate `self+0x110+4*i`. Register the result with the retained
   owner using veneers `0x060` and `0x068`. Invoke vtable `0x108` with the
   related inline record selected by descriptor word 1, then vtable `0x100`
   with descriptor byte 8. If descriptor byte 9 is zero, invoke vtable `0xD4`
   with `s0=0.0f`.
3. Fetch two halfword flags through veneer `0x020`, using the two caller tokens
   in pool `0x6EC` and `0x6F0`. If the first is nonzero, for `i=0..3` invoke
   vtable `0xCC` on arrays at `+0x124` with `1.0f` and `+0x114` with `5.0f`.
   If it is zero and the record state is 2, call `func_000006FC` using record
   bits 8..15, then invoke `0xCC` with `5.0f` on the selected `+0x114` object.
4. If the second flag is nonzero, invoke `0xCC` with `1.0f` on `*(self+0x130)`
   and with `5.0f` on `*(self+0x120)`.
5. Store 4 to byte `self+0x134` and return.

### `func_000006FC` — snapshot refresh

This is the previously accepted 152-byte function. Its neutral behavior is:

1. Copy the three words at `*(self+0x10)` to a stack record and set `s0=1.0f`.
2. Invoke vtable `0xCC` on `*(self+0x124+4*index)`.
3. Replace byte 1 of the stack record by `index`.
4. Construct a 64-byte temporary using owner field chain `self+8`, then call
   veneers `0x078`, `0x080`, and `0x088` in that order.
5. Copy the first three words of the updated stack record back to
   `*(self+0x10)` and return.

### `func_00000798` — movement-change handler

Read the current 12-byte record. Select an object in the `+0x114` array from
bits 8..15 and call vtable `0xD0`. If returned `s0` is greater than `5.0f`,
invoke its `0xCC` with `s0=5.0f`, then `0xD4` with `s0=0.0f`.

Build the same 64-byte temporary as `func_000006FC`, pass it through veneers
`0x070`, `0x078`, `0x080`, and `0x088`, and obtain two output words. If they
equal record words 1 and 2, return. Otherwise derive a secondary index from
record bits 16..23:

- If it is 3, set record state to 1 while preserving the index and the old two
  coordinate words.
- Otherwise invoke `0xCC` with `s0=0.0f` on `*(self+0x124+4*secondary)`, set
  record state to 1 while preserving its other words, and invoke `0xD4` with
  `s0=1.0f` on the object selected from `+0x114` by bits 8..15.

### `func_00000920` — startup state machine

Read byte `self+0x134`; return value defaults to zero.

- Phase 0: call veneer `0x090(*(self+0x0C),pool_A14,0)`, then advance the phase.
- Phase 1: call veneer `0x098(*(self+0x0C))`; advance only on nonzero result.
- Phase 2: follow the owner chain from `self+8` to a structure at offset
  `0x12EC`. If its pointer field at `+4` is null, call veneer `0x0A0`; otherwise
  call veneer `0x0A8(...,0)`. Then call veneer `0x0A0` with the structure and
  its pointer field, store the returned three-word record at `self+0x10`, and
  clear those three words only when the original pointer field was non-null.
  Advance the phase.
- Phase 3: return 1 without advancing. Other values return 0.

### Constructors and global initializer

- `func_00000A18(r0,r1)`: write `r1` to offsets 4 and 8, write the vtable
  identity `.rodata+0x174` to offset 0, call veneer `0x0B0` for nine elements
  of size `0x1C` starting at offset `0x14`, clear byte `0x134`, allocate 64
  bytes using owner fields through veneer `0x0B8`, conditionally initialize
  that allocation through veneer `0x0C0` with the `.rodata+0x6C` identity,
  store it at offset `0x0C`, and return the original object.
- `func_00000AA8(r0)`: store `.rodata+0x174`, call veneer `0x0C8` for nine
  elements at `+0x14`, then tail-call veneer `0x018` on the original object.
- `func_00000ADC(r0)`: store `.rodata+0x174`, call veneer `0x0C8` for nine
  elements at `+0x14`, and return the original object.
- `func_00000B10()`: load `.bss+0`; store `0.7f` to offsets 0 and 4 and
  `1.0f` to offsets 8 and 12; return.

### `nnroControlObject_` at `0xB3C`

This is the sole named export. It dispatches on unsigned operation `r1`; values
0..4 use a five-entry inline jump table and values above 4 take the default.

- 0: store the literal at `0xBC8` through `r0`.
- 1: store `r0` in the single word `.data`; return 0.
- 2: load `.data` and store it through `r0`; return 0.
- 3: store the relocated text identity from `0xBCC` at `r0+0`, and the one from
  `0xBD0` at `r0+4`; return 0.
- 4: store the relocated rodata identity from `0xBD4` at `r0+0`, and the one
  from `0xBD8` at `r0+4`; return 0.
- default: return a value selected through loader-patched control literals in
  `0xBA8..0xBC4`.

The inline table contains five relocated `.text` identities between the
dispatcher and its case bodies.

## Implementation and validation requirements

An independent implementer should use address-derived names, ARM state, the
listed object offsets, loop bounds, literal identities, and call ordering. Do
not transcribe target bytes, the omitted type-name payloads, or opaque table
payloads. Exact matching of proprietary name/table regions is explicitly out
of scope unless an independently authored equivalent is available.

Validation must prove all of the following:

1. `.text` is exactly 3,052 bytes and is partitioned into 2,760 instruction
   bytes plus 292 literal/jump-table bytes with no unknown range.
2. All 26 veneers use the two-word ARM absolute-jump shape and the listed
   identity order.
3. The 26 local boundaries, embedded pool ranges, ARM mapping symbols, and
   sole export at `0xB3C` agree with this specification.
4. `.rodata`, `.data`, and `.bss` have sizes 428, 4, and 16 respectively; the
   header BSS reservation remains 48.
5. There are exactly 33 import and 44 internal relocations, all
   `R_ARM_ABS32`, with the outputs, identities, and addends above.
6. No extra relocation, allocated section, unexplained byte, or overlapping
   ownership remains. Compare section digests only in private verification.

Known clean-room limitation: 96 observed `.rodata` bytes are proprietary type
name payloads, and 200 additional non-relocation `.rodata` bytes are compact
descriptors/identifiers. They are fully range-accounted but intentionally not
reproduced here. A byte-identical complete CRO therefore remains blocked on an
independently authored source for those payloads; code, boundaries, literal
layout, and relocation accounting are otherwise complete.
